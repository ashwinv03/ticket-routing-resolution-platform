1. CORE ARCHITECTURE & 4 GB RAM DESIGN PRINCIPLES
================================================================================

A standard machine learning approach (loading BERT, RoBERTa, or LLaMA locally) 
requires 2 to 6+ GB of RAM just for model weights, resulting in browser tab crashes, 
heavy disk swap thrashing, and freezing on 4 GB laptops.

This platform solves that constraint through a high-efficiency architecture:

1. In-Process Zero-Daemon Database (PySQLite):
   - SQLite is compiled directly into Python's runtime via `sqlite3`.
   - Requires zero background server daemons (unlike MySQL or MongoDB which consume 
     300–600 MB of RAM at idle).
   - Entire database resides in a single local file (`tickets.db`) with instant ACID 
     transactions and zero memory overhead.

2. Cloud LLM API Offloading:
   - Intelligence operations (ticket summarization, resolution suggestions, and 
     draft response generation) are offloaded to Cloud LLM APIs (e.g. Google Gemini 
     API / Groq).
   - The laptop only sends lightweight HTTP JSON payloads (< 5 KB) and receives text.
   - Built-in heuristic offline fallback ensures the platform never fails even if 
     internet is disconnected during an exam defense.

3. Total Resource Footprint:
   - Operating memory usage of the entire backend and database: < 150 MB RAM.
   - Leaves over 3.5 GB of RAM free for the operating system and browser.

2. COMPLETE FUNCTIONALITY BREAKDOWN
================================================================================

[A] Two-Stage Intelligent Routing Engine
  * Stage 1 - Configurable Keyword/RegEx Department Routing:
    - Scans incoming ticket title and description against active `RoutingRule` entries 
      ordered by precedence (`priority_order`).
    - Routes ticket directly to the appropriate team (e.g. VPN -> Network & Infrastructure, 
      SQL crash -> Software & Applications, Docker/K8s -> Cloud & DevOps).
    - Can optionally enforce a priority override.
  * Stage 2 - Workload-Aware Agent Allocation:
    - Queries all active personnel (`agent` and `team_admin`) assigned to that department.
    - Computes each member's active ticket load (tickets in 'assigned', 'in_progress', 
      'pending_user').
    - Assigns the ticket dynamically to the member with the minimum active load.
    - If no agents are configured, leaves ticket in the team unassigned pool.

[B] ITIL SLA & Priority Matrix Engine
  * ITIL Priority Matrix:
    - Priority is determined dynamically from Urgency (Low/Medium/High) x Impact (Low/Medium/High).
    - Prevents requesters from arbitrarily tagging every ticket as 'Critical'.
    - Yields standard ITIL priority tiers: P1 (Critical), P2 (High), P3 (Medium), P4 (Low).
  * Response & Resolution Countdown:
    - Sets Time to First Response (TTFR) and Time to Resolution (TTR) deadlines based on `SLAPolicy`.
    - Real-time comparison flags SLA breaches when current time exceeds due date.
  * Fair SLA Clock Pausing:
    - When a ticket status transitions to 'Pending User' (waiting for user details/logs), 
      the SLA clock records `paused_at`.
    - When the requester replies or the agent reactivates the ticket, the elapsed pause 
      duration is added to `total_paused_seconds` and the target due date is pushed forward.
  * Requester Confidentiality:
    - SLA countdown timers and breach warning badges are hidden from requesters.
    - Prevents customer agitation; strictly treated as internal support performance targets.

[C] Universal Ticket Search
  * Located prominently in the top navigation bar.
  * Exact Ticket # Matching: Entering `INC-20261120-0001` or `inc-20261120-0001` redirects 
    instantly to that ticket's workstation page.
  * Substring / Digit Matching: Entering `0001` or `0002` locates the matching ticket directly.
  * Keyword Fallback: Entering a title or topic filters the ticket queue with search results.
  * Enforces role security (requesters can only search and view their own tickets).

[D] Agent Workstation & AI Assistant
  * Dual-Channel Conversation:
    - Public Replies: Visible to the end-user requester.
    - Internal Private Notes: Highlighted in amber with lock icons, strictly visible only 
      to agents, team admins, and global admins.
  * File Attachments:
    - Upload screenshots and logs (`.png`, `.jpg`, `.pdf`, `.txt`, `.docx`) saved to static/uploads.
  * AI Resolution Assistant (Cloud LLM API):
    1. Summarize Ticket: Generates a 3-bullet executive summary (core problem, actions taken, 
       pending blocker) from long ticket conversations.
    2. Suggest Resolution: Retrieves top matching Knowledge Base articles from SQLite and 
       synthesizes step-by-step diagnostic advice for the agent.
    3. Draft Response: Generates a polite, context-aware reply to the requester, featuring a 
       1-click button to insert the generated draft directly into the comment box.
  * Reassignment Modal:
    - Allows agents and leads to transfer a ticket to another department or specific agent.
    - Agent dropdown groups personnel by department `<optgroup>` and displays their real-time loads.
  * Full Lifecycle History (Audit Trail):
    - Dedicated tab tracking ticket creation, routing rule match, auto-assignment, status changes, 
      and reassignment with timestamps and user attribution.

[E] Searchable Knowledge Base (Self-Service & Agent Assistance)
  * Publicly searchable repository of troubleshooting guides and standard operating procedures.
  * Full-text keyword search across titles, contents, and comma-separated tags.
  * Article view counter to identify high-frequency recurring issues.
  * Acts as ground-truth retrieval context for the AI Resolution Recommender.

[F] Department & Team Administration (Global & Scoped)
  * Global Admin Console:
    - Operational Dashboard with Chart.js charts (Priority distribution doughnut, Status breakdown bar).
    - Department CRUD: Create new teams, edit team name/description, assign Team Leads, and 
      delete teams with safe member/ticket unassignment.
    - Configurable routing rules table (precedence, keywords, matching field, target team).
    - SLA policy editor for P1..P4 response and resolution targets.
    - User management console (roles, active toggles, team assignments).
  * Team Admin Console (Department-Scoped):
    - Access isolated strictly to the assigned team.
    - Departmental Analytics Dashboard (team tickets, open queue, team SLA compliance %, team CSAT).
    - Manage Team Agents: View team staff workloads, add existing users to the team, register 
      new agents directly into the team, or remove agents.
    - Department Routing Keywords: Manage keyword rules that route tickets to this department.

[G] Customer Satisfaction (CSAT) Rating
  * When a ticket is marked 'Resolved' or 'Closed', the requester is presented with a 1 to 5 star 
    rating widget and optional feedback textarea.
  * Feeds into agent and team quality scores on the analytics dashboards.

4. TICKET LIFECYCLE STATE MACHINE & SLA ENGINE
================================================================================

Lifecycle State Flow:
  [New] 
    --> [Assigned] (via automated 2-stage routing engine)
    --> [In Progress] (agent acknowledges & diagnoses)
    --> [Pending User] (waiting for requester info -> SLA CLOCK PAUSED)
    --> [In Progress] (requester replies -> SLA CLOCK RESUMED)
    --> [Resolved] (solution provided; CSAT rating unlocked for requester)
    --> [Closed] (confirmed resolved or auto-closed)
    --> [Reopened] (requester indicates issue persists -> returns to active work)

SLA Policy Matrix:
Priority Level | First Response Target | Resolution Target | Escalation Warning
---------------+-----------------------+-------------------+-------------------
P1 - Critical  | 0.5 Hours (30 mins)   | 4.0 Hours         | 75% elapsed warning
P2 - High      | 1.0 Hour  (60 mins)   | 8.0 Hours         | 80% elapsed warning
P3 - Medium    | 4.0 Hours             | 24.0 Hours        | 2 hours remaining
P4 - Low       | 8.0 Hours             | 48.0 Hours        | Standard queue

6. EVALUATOR / VIVA Q&A DEFENSE PREPARATION
================================================================================

Q1: Why did you use PySQLite instead of MySQL, PostgreSQL, or MongoDB?
A1: "For enterprise scalability in cloud production, PostgreSQL or MySQL are standard. 
However, for an academic bachelor's project specified to run on a resource-constrained 
4 GB RAM development laptop, traditional database daemons consume 300 to 600 MB of RAM at idle. 
PySQLite provides full ACID compliance, relational integrity, foreign key constraints, and 
zero server overhead by running directly in-process within the Python runtime. The entire schema 
is managed through SQLAlchemy ORM, meaning migrating from SQLite to PostgreSQL in production 
requires changing only a single connection string."

Q2: Why did you not train a local machine learning model for routing?
A2: "Training or running BERT or transformer models locally on a 4 GB RAM machine without a dedicated 
GPU causes out-of-memory errors and operating system freezing. Furthermore, in real-world ITIL 
operations, organizations require deterministic, auditable routing rules that team leads can 
instantly update without re-annotating datasets and retraining neural networks. We combined a 
high-speed deterministic two-stage keyword/workload engine with cloud LLM APIs for generative tasks, 
achieving sub-second response times with zero local memory overhead."

Q3: How does your workload-aware assignment algorithm work?
A3: "When a ticket matches a department, the system computes the active load for each active staff 
member in that department:
   Active Workload = count(tickets where status in ['assigned', 'in_progress', 'pending_user'])
The algorithm selects the agent with min(Active Workload). This eliminates bottlenecking where a fast 
agent gets overloaded while others remain idle."

Q4: How does SLA clock pausing work mathematically?
A4: "When status changes to 'pending_user', the timestamp is stored in `paused_at`. When the ticket 
is resumed, the elapsed pause time in seconds is calculated:
   paused_seconds = (now - paused_at)
This duration is added to `total_paused_seconds` and the target resolution deadline is pushed forward:
   due_date = due_date + timedelta(seconds=paused_seconds)
This ensures neither the agent nor the organization is penalized for delays caused by customer response times."

Q5: Why is SLA information hidden from the requester?
A5: "In ITIL and customer service standards, SLAs are internal operational agreements between support 
management and IT teams. Exposing internal breach timers to customers causes unwarranted friction and 
distracts from the actual resolution process. Support agents and supervisors retain full visibility."
